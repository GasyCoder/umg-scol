# Décisions d'architecture

- ADR-001 : un seul backend Laravel 13 / PHP 8.4+, Inertia pour le portail interne et API dédiée pour le portail étudiant (voir ADR-009).
- ADR-002 : React + TypeScript + shadcn/ui.
- ADR-003 : MySQL.
- ADR-004 : aucun module d'inscription universitaire.
- ADR-005 : séparation `Student` / `StudentRecord`.
- ADR-006 : dossier de bourse papier en V1 ; le système trace le traitement.
- ADR-007 : audit obligatoire, y compris développeur.
- ADR-008 : import massif avec prévisualisation obligatoire.
- ADR-009 : deux portails : `scol.umg.test:8000` pour Scolarité Centrale, établissements, superadmin et developer ; `bourse.umg.test:8000` pour les étudiants uniquement. API prévue sous `/api/student/*`, dans le même backend. Cette décision remplace l'hypothèse initiale d'une V1 sans API étudiante. Routage par domaine et endpoints étudiants implémentés (voir ADR-035).
- ADR-010 : authentification étudiante prévue par email + OTP ou Google OAuth, puis rattachement sécurisé à une fiche `Student` existante. Un compte vérifié ne vaut ni inscription universitaire ni preuve de propriété d'une fiche. Précisé par ADR-035 à ADR-037.
- ADR-011 : l'étudiant propose une correction ; l'établissement décide de la modification des données officielles. Aucun accès étudiant en écriture directe à l'identité administrative.
- ADR-012 : MySQL est le moteur local et celui du setup CI ; SQLite en mémoire est conservé pour les tests existants. Le fichier SQLite local résiduel est conservé jusqu'à une décision explicite de nettoyage.

- ADR-013 : fondation d'accès avec Spatie Permission, cinq rôles et 33 permissions explicites. Superadmin et developer ont le catalogue complet sans bypass global ; la portée réelle sera contrôlée par les futures Policies métier.
- ADR-014 : provisionnement superadmin par variables d'environnement et seeder transactionnel idempotent, sans compte de démonstration, sans mot de passe codé en dur et sans rotation implicite du mot de passe existant.
- ADR-015 : désactivation globale de l'inscription Fortify actuelle tant que le routage par domaine est absent. La future inscription étudiante sera mise en place séparément, sans réouverture de la création publique de comptes administratifs.
- ADR-016 : audit synchrone de User par liste de champs autorisés et audit des attributions/retraits Spatie. Aucune exception developer, aucune journalisation de secrets, aucune purge automatique.

- ADR-017 : référentiels institutionnels administrables par les permissions existantes, avec routes web Inertia, pagination serveur et désactivation. Aucune liste officielle UMG ni donnée de démonstration n'est seedée.
- ADR-018 : au plus une année courante, garantie par index unique sur une colonne générée nullable. Changement transactionnel avec verrouillage ordonné, mises à jour Eloquent auditées et retrait du statut courant lors de la désactivation. Aucun effacement des années historiques.
- ADR-019 : code de parcours unique par établissement lorsqu'il est renseigné ; nom libre et non unique globalement. FK restrictives vers les établissements ; aucune relation niveau/parcours imposée.
- ADR-020 : rattachement utilisateur/établissement nullable en base, avec Action validée et contrôle de contexte sur les routes métier internes. Les comptes établissement sans rattachement actif sont inexploitables sur ces routes ; aucun CRUD utilisateur n'est créé dans cette phase.
- ADR-021 : audit des champs structurels des référentiels ; les changements limités aux contacts sont tracés sans leurs valeurs. Programmes et établissements sont filtrés par périmètre lorsque le rôle établissement reçoit une permission de gestion, sans modification de la matrice initiale.

- ADR-022 : identité permanente Student distincte de StudentRecord annuel. Le module centralise les étudiants déjà régulièrement inscrits hors plateforme ; aucune inscription/admission/paiement universitaire.
- ADR-023 : identifiants personnels indexés sans UNIQUE global en base. La saisie manuelle normalisée bloque les doublons évidents sous verrou partagé ; aucun rapprochement automatique ou exposition d'identité étrangère. La qualité des données historiques et les similitudes seront traitées avec le futur import.
- ADR-024 : une fiche par étudiant/année/établissement et au plus une fiche annuelle active par étudiant/année via index généré nullable. Historique conservé, transfert uniquement après désactivation explicite par des acteurs autorisés ; aucune mutation silencieuse de l'année ou de l'établissement d'une fiche.
- ADR-025 : parcours cohérent avec l'établissement par validation serveur et FK composite. Statuts active/inactive concernent uniquement la déclaration dans la plateforme ; identité et déclaration ont des activations distinctes.
- ADR-026 : établissements limités à leurs déclarations et à leurs identités visibles ; une identité partagée historiquement ne peut être corrigée globalement que par un acteur autorisé global. Scolarité Centrale en lecture seule, comptes student explicitement refusés, aucun lien User étudiant vers Student dans cette phase.
- ADR-027 : audit Student par noms de champs modifiés, sans valeurs personnelles ; audit annuel par IDs/statut/acteur/dates administratives. Création identité + première déclaration et modifications annuelles transactionnelles, audit inclus.
- ADR-028 : liste interne par déclaration annuelle, pagination SQL de 20 lignes, recherche par préfixe des identifiants/contacts et sous-chaîne des noms. Eager loading ciblé ; aucune exportation ou API étudiante ajoutée.

- ADR-029 : pipeline StudentImport/StudentImportRow persisté, aucune écriture Student/StudentRecord avant confirmation. Laravel Excel 4.0.4, XLSX et CSV uniquement, une feuille avec headers. XLS converti en amont ; pas de support arbitraire des formats historiques binaires.
- ADR-030 : mapping déterministe des 17 colonnes, alias français et correction manuelle ; normalisation Student partagée ; calendrier Excel 1900/1904 conservé entre requêtes. Pas de moteur IA ni référentiels créés silencieusement.
- ADR-031 : union prudente des identifiants forts et de l'identité avec naissance ; plusieurs candidats = revue sans fusion. Compléter uniquement les valeurs DB vides ; tout conflit non vide, contacts inclus, reste warning. Identité partagée/étrangère inaccessible à l'établissement pour import automatique. Déclaration identique = duplicate ; contradiction/actif étranger = warning, aucun transfert.
- ADR-032 : seuls valid importables ; warnings/rejected/duplicate ignorés. Transaction globale, import verrouillé et completed idempotent, matching revalidé sous verrous ciblés SHA-256 partagés avec la saisie manuelle. Référentiels verrouillés en lecture partagée, candidats en écriture ; pas d'appel par ligne à CreateDeclaredStudent sous verrou global.
- ADR-033 : V1 synchrone bornée à 10 Mo / 5 000 lignes / 50 colonnes, chunks de 200, staging inséré par blocs, preview 25 lignes et historique 20 lignes avec eager loading. Le passage en Jobs sera justifié par les mesures de charge du déploiement, sans prétendre à un benchmark institutionnel complet.
- ADR-034 : fichier privé sans route publique, formules non exécutées/rejetées, expansion ZIP bornée, erreur CSV sans PII. Audit upload/analyse/commit par métadonnées et compteurs. Purge quotidienne fichiers/staging après 30 jours, compteurs conservés ; nécessité d'activer le scheduler et d'aligner les sauvegardes en production.
- ADR-035 : portail étudiant = SPA React dédiée sur `bourse`, même backend, Sanctum en session/cookie (pas de jeton Bearer). Garde `student` séparé du garde `web` (provider `internal`), cookies de session distincts et host-only par portail, hôte inconnu = 404.
- ADR-036 : OTP email à 6 chiffres, haché, 10 minutes, 5 tentatives, lié à la session ; demandes limitées par IP et par adresse (3/min, 10/h, 20/jour) pour borner la force brute dans la durée ; envoi refusé via le mailer `log`. Google OAuth seulement avec email vérifié ; le nom Google n'est jamais repris dans l'identité. L'email vérifié ouvre un compte numérique sans accès à une fiche.
- ADR-037 : rattachement automatique strict (identifiant exact + naissance + candidat unique actif + même email officiel vérifié) ; sinon demande soumise à l'approbation du personnel, revalidée sous verrou au moment de la décision. Établissement : demandes liées à une déclaration active de l'année courante ; Scolarité Centrale : revue globale. Une fiche = un compte au plus, garanti en SQL.
- ADR-038 : demande de correction = un champ par demande, au plus une demande pending par étudiant et champ (unique SQL sur colonne virtuelle). Statuts `pending → approved | rejected | cancelled`, sans retour ; annulation par l'étudiant, pas d'édition. Liste blanche des champs Student (14 depuis ADR-066) ; toute la déclaration annuelle est exclue (contacter l'établissement).
- ADR-039 : pas de copie de la valeur actuelle ; empreinte HMAC de la valeur observée et contrôle de cohérence optimiste à l'approbation (conflit = blocage, revue manuelle). Valeur proposée chiffrée au repos. Approbation par `SaveStudentIdentity::persist` dans la transaction de décision pour réutiliser autorisation, verrous et contrôles de doublons.
- ADR-040 : revue selon la matrice existante : établissement sur son périmètre (déclaration active de l'année courante, scope partagé avec les rattachements) et seulement s'il peut modifier l'identité ; Scolarité Centrale en lecture seule globale ; superadmin/developer global. Motif de refus unique visible par l'étudiant en V1. `Student.email` (contact officiel) n'est jamais synchronisé avec `User.email` (connexion). Pas de notification email/SMS en V1 : statut visible dans « Mes demandes ».
- ADR-041 : la demande de bourse reste papier ; `ScholarshipApplication` représente le dossier reçu et traité par la Scolarité Centrale, rattaché à l'étudiant et à l'unique déclaration active de l'année de la campagne, sans recopie des données personnelles. Aucun dépôt numérique, upload ni statut visible côté étudiant en V1.
- ADR-042 : campagnes `draft → scheduled | open → closed → archived` gérées par une permission par action (`campaigns.view|create|update|open|close`, attribuables par rôle ; à l'origine `campaigns.manage`), transitions manuelles, réception uniquement en `open`, traitement possible jusqu'à l'archivage. Numéro de dossier technique `BRS{campagne}-{séquence}` attribué sous verrou de la campagne. DDB conservé en chaîne libre, unique seulement par campagne (clé sans espaces, en majuscules), faute de format réglementaire connu.
- ADR-043 : statuts dossier `pending`, `in_review`, `validated`, `needs_correction`, `rejected` ; décisions définitives non réouvrables en V1 ; motif obligatoire pour correction et rejet ; `needs_correction` ne touche jamais `Student`. Checklist générique configurable (identité, déclaration, BAC, coordonnées, complétude), stockée par contrôle et non en JSON, exigée conforme/non applicable pour valider ; à remplacer par la liste officielle de la Scolarité Centrale.
- ADR-044 : historique métier dédié (`scholarship_application_status_histories`) en plus de l'ActivityLog technique ; `review_started_*` désigne le dernier début de vérification et `decided_*` la seule décision définitive. Accès global par les permissions `scholarships.*` existantes, sans nouvelle permission ; établissements et étudiants exclus.
- ADR-045 : confirmation étudiante = trace de vérification par l'étudiant des informations affichées, sans effet sur les données officielles ni sur le traitement papier des bourses (jamais un prérequis de réception, vérification ou validation). Porte sur les champs visibles de l'identité, des contacts et du BAC et sur la déclaration active de l'année courante, résolue côté serveur ; refus si aucune année courante, aucune déclaration, déclaration inactive, situation ambiguë ou correction `pending`. Données CIN exclues car jamais affichées ; `Student.email` confirmé sans lien avec `User.email`.
- ADR-046 : table `student_information_confirmations` historisée (rang unique par étudiant), sans copie de données personnelles ; empreinte HMAC-SHA256 keyée par `APP_KEY` (même convention que les corrections) sur un encodage canonique versionné (clés ordonnées, valeurs préfixées par leur longueur), incluant identifiants **et libellés affichés** des référentiels. État `never_confirmed` / `confirmed` / `stale` déduit à la lecture (dernière confirmation comparée à l'empreinte courante), jamais stocké ni mis à jour par les autres Actions. Rotation d'`APP_KEY` = toutes les confirmations obsolètes (échec sûr). Une nouvelle année courante exige une nouvelle confirmation.
- ADR-047 : `POST /api/student/confirmation` sans données Student, avec seulement un jeton opaque de la version affichée (HMAC dérivé, distinct de l'empreinte) pour qu'une version modifiée entre l'affichage et le clic ne soit jamais confirmée. Transaction avec verrous compte → fiche → déclaration (ordre partagé avec les corrections), idempotence pour une même version, audit par identifiants seulement. Le personnel voit l'état, la date et l'année sur la fiche interne, selon `StudentPolicy`.
- ADR-048 : URL Wayfinder relatives au portail courant : les routes `scol` (et Fortify) ne sont pas liées à leur domaine pendant `wayfinder:generate`, uniquement pour la génération ; le routage par `Route::domain()` reste la règle à l'exécution. Les routes `bourse` restent liées (SPA sans Wayfinder, et `/` y entrerait en conflit avec `home`). `/` sur `scol` redirige vers le tableau de bord (connexion pour un invité) au lieu de la page d'accueil du starter kit. Chaque limitation de débit interne a son propre compteur (préfixe du middleware `throttle`), pour qu'une série de contrôles ou de décisions ne bloque ni l'export ni le changement de mot de passe.
- ADR-049 : tableaux de bord et rapports sans nouvelle permission : chaque bloc dépend de la Policy du module, dans un périmètre serveur (`ReportScope`) ; année courante par défaut (jamais la dernière ligne), filtre d'année réservé aux acteurs globaux sur le tableau de bord. Agrégats SQL partagés entre tableau de bord et rapports, graphiques en barres CSS simples avec valeurs écrites (pas de bibliothèque de graphiques). Pas de cache tant que les mesures ne le justifient pas.
- ADR-050 : interface d'audit lecture seule (`audits.view`, `audits.export`) avec un présentateur à liste blanche comme unique sortie des journaux ; JSON brut jamais affiché ni exporté ; comptes étudiants anonymisés ; developer traité comme tout acteur. Exports CSV par `CsvExport` (anti-injection de formules) et audités.
- ADR-051 : application en français (`APP_LOCALE=fr`, `APP_FALLBACK_LOCALE=fr`, fichiers `lang/fr`), écrans du starter kit traduits. Marque neutre « UMG Bourse » avec un monogramme typographique « UMG », sans blason officiel ni ressource externe.
- ADR-052 : mention = référentiel par établissement (`mentions`), parcours rattaché facultativement à une mention du même établissement (FK composite) ; mention de l'étudiant déduite du parcours, sans duplication dans les déclarations ni l'import ; gestion par `programs.manage`.
- ADR-053 : liste des étudiants en navigation par cartes (établissement → niveau → mention → parcours → liste), comptages SQL agrégés dans le périmètre de l'acteur et pour une année (courante par défaut).
- ADR-054 : thème du portail interne inspiré du template DashWind (palette, typographie Roboto/Nunito, cartes, barre latérale bordée) appliqué aux tokens shadcn/ui, sans reprendre les composants ni les dépendances du template. Le template reste une référence locale non versionnée (`template-model/`, ignoré par git, le formateur et le lint).
- ADR-055 : identifiant public UUID v7 pour les étudiants dans les URL, l'`id` entier restant clé primaire et cible des FK. Fiche étudiant présentée en page profil compacte (carte d'identité, situation de l'année courante, vérification étudiant, informations officielles groupées, déclarations en tableau).
- ADR-056 : UUID v7 public étendu à tous les enregistrements adressés par URL (référentiels, déclarations, imports, corrections, rattachements, campagnes, dossiers, entrées d'audit) via le trait `HasPublicUuid` et un modèle `App\Models\Activity` pour l'audit ; l'`id` entier reste clé primaire, cible des FK et valeur des formulaires ; l'identifiant numérique dans une URL répond 404.
- ADR-057 : mise en page du portail interne alignée sur DashWind : barre supérieure fixe (menu, fil d'Ariane, compte avec rôle), barre latérale à sections, titres de page « Section / élément », fiches de détail en carte à onglets avec panneau latéral, et pages en pleine largeur (aucun conteneur centré à largeur maximale).
- ADR-058 : import/export des mentions et parcours en XLSX (modèle avec feuille « Codes », export filtré réimportable, CSV accepté à l'import) sans table de staging : analyse → cache 30 min sous jeton lié au compte → prévisualisation → confirmation qui réanalyse sous verrou et écrit en une transaction par Eloquent ; une ligne sans code ne met jamais à jour (doublon probable si le nom existe), les lignes en erreur ne sont jamais importées, audit `references_imported` par compteurs.

- ADR-059 : cinq rôles et catalogue fixes, matrice des permissions en base pilotée par `/permissions` (`permissions.manage`) ; seeder initialise seulement les nouveautés, ne réécrit pas les réglages. Trois droits de récupération superadmin obligatoires, liste blanche student, audit des différences et sauvegarde avec contrôle de version.
- ADR-060 : suppression réversible des dix catégories administratives par corbeille (`trash.manage`/`trash.purge`, superadmin/developer), garde-fous sur les références utilisées, cascade Student/déclarations par lot, restauration avec contrôle des conflits, purge séparée des données non dépendantes ; dossiers déjà traités et audit protégés. Unicités des déclarations/année courante limitées aux lignes visibles ; codes de référentiels réservés en corbeille.
- ADR-061 : purge d'import sans effet sur les étudiants importés ; suppression de fichier après commit et outbox de reprise horaire. Les imports en corbeille restent soumis à la rétention du staging. Scopes de corbeille explicites dans les jointures, validations et revues ; UUID conservés.
- ADR-062 : refonte UI/UX du portail interne, remplaçant le thème DashWind (ADR-054) et précisant la mise en page (ADR-057) : palette institutionnelle (bleu roi, barre latérale marine, accent or), Public Sans / Plus Jakarta Sans, tokens de statut (succès, attente, info, danger) en clair et en sombre, bascule de thème dans la barre supérieure, illustrations SVG dessinées avec les tokens (aucune image externe), recherche de pages Ctrl K limitée à la navigation. Cloche de notifications = travail en attente calculé à la lecture par `PendingTasks` dans le périmètre des Policies, sans table ni état lu. Règles et composants dans `docs/UI_DESIGN.md`.
- ADR-063 : gestion des comptes internes (`/users`, `users.manage`, acteur global non établissement), remplaçant la réserve d'ADR-020. Un seul rôle interne par compte, droits par défaut du rôle (matrice ADR-059) ajustables par compte : ajouts = permissions directes Spatie, retraits = table `user_denied_permissions` appliquée dans `User::hasPermissionTo()`/`getAllPermissions()` (donc dans Gate, Policies et menu). Ajuster les droits exige en plus `permissions.manage` ; catalogue uniquement, version optimiste, audit `user_permissions_updated`. Création sans mot de passe connu : invitation par lien de réinitialisation (validité du broker). Suspension réversible (`is_active`) : connexion refusée avec message seulement si le mot de passe est correct, sessions fermées. Garde-fous : aucune action sur son propre compte, au moins un superadmin actif, droits de récupération du superadmin non retirables, comptes developer visibles et attribuables par un developer seulement, comptes étudiants exclus, UUID public dans les URL.
- ADR-064 : fiche établissement : le `code` est présenté comme « sigle » (colonne inchangée, déjà utilisée par imports et exports) ; type au choix Faculté, Institut, École ou « Autre » en texte libre, stocké comme texte (les valeurs existantes restent valides). Logo facultatif PNG/JPG/WebP ≤ 1 Mo (SVG refusé : scripts possibles), stocké sur le disque privé et servi par `GET /references/establishments/{uuid}/logo` selon `EstablishmentPolicy::view`, URL versionnée ; nouveau fichier écrit avant la transaction et supprimé en cas d'échec, ancien fichier supprimé après commit via l'outbox de fichiers (remplacement, retrait, purge).
- ADR-065 : identité de la plateforme réglable dans Paramètres → Plateforme (nouvelle permission `branding.manage`, superadmin/developer, acteur global) : nom de l'institution, nom du portail interne (scol), nom du portail étudiant (bourse), email de contact, logo (PNG/JPG/WebP ≤ 1 Mo) et favicon (PNG carré ≤ 256 Ko). Table clé/valeur `platform_settings`, valeurs par défaut si vides, cache invalidé après commit. Logo et favicon publics (`/branding/{logo|favicon}` sur les deux domaines, URL versionnée, `nosniff`, CSP restrictive) car affichés avant connexion ; SVG refusé. Partagés via Inertia (`branding`, `name`) sur scol et via `data-branding` du blade sur bourse ; titre d'onglet dynamique. Audit `branding_updated` (module `platform`), anciens fichiers supprimés après commit via l'outbox.
- ADR-066 : le fichier Excel modèle des établissements devient la source de vérité des données étudiantes. Identité : sexe, nom de la mère et nationalité ajoutés ; matricule, numéro BAC, lieu de naissance et mention BAC supprimés (absents du modèle). Rattachement du portail par CIN + date de naissance. Téléphone et email uniques par contrôle applicatif et verrous d'identité (pas d'index UNIQUE SQL : fiches historiques et corbeille) ; CIN de 12 chiffres = clé d'identité, autre valeur acceptée et signalée « non standard ». Déclaration annuelle : code de redoublement, date et référence de la demande de bourse (référence unique par établissement/année, index SQL limité aux lignes hors corbeille). Domaine (référentiel global sur la mention, permission `levels.manage`), type de formation (parcours) et institution (établissement) sont des attributs de référentiels contrôlés à l'import, pas des valeurs recopiées. BOURSIER/TAUX ne sont pas importés : règle recalculée par `ScholarshipEligibility` avec une année limite du BAC par année universitaire, indicative et sans effet sur le traitement papier. L'import accepte le modèle tel quel (légende et totaux ignorés).
- ADR-067 : désactiver un étudiant désactive aussi ses déclarations actives de l'année courante (marque `inactive_with_identity`, migration `2026_10_17_110000` appliquée aussi aux identités déjà inactives) ; la réactivation ne restaure que ces déclarations. Remplace la règle « désactiver l'identité ne réécrit pas les déclarations » : la liste et les compteurs reflètent ainsi la désactivation. Les années passées restent l'historique.
- ADR-068 : l'import d'étudiants crée les mentions et parcours manquants de son établissement (et un domaine écrit « (CODE) Nom ») à la confirmation, sans autre permission que `imports.commit` : la création reste limitée à l'établissement de l'import, annoncée en prévisualisation (`student_imports.reference_changes`), transactionnelle et auditée. Les niveaux restent gérés par l'administrateur, sauf les niveaux LMD standard (L1 à M2), créés par l'import s'ils manquent. Un référentiel inactif ou ambigu bloque la ligne au lieu d'être dupliqué.
- ADR-069 : `/students` garde la navigation par cartes (ADR-053) comme vue par défaut et ajoute la vue « Tous les étudiants » (`view=list`) : liste unique de tout le périmètre avec l'établissement de chaque ligne et tous les filtres ; recherche, statut ou « toutes les années » ouvrent la liste ; l'export suit les filtres de la liste.
- ADR-070 : import multi-établissements pour les acteurs globaux (sans établissement sur l'import, établissement lu sur chaque ligne par sigle puis nom) ; code de redoublement P (Passant), éligible au taux 1 comme N ; sexe et nationalité facultatifs à l'import quand la colonne est absente (toujours exigés en saisie manuelle).
- ADR-071 : rattachement du portail sans CIN obligatoire : date de naissance + un identifiant au choix (CIN, téléphone, email déclarés, ou nom de famille). Règle de sécurité inchangée (automatique seulement si l'email officiel de la fiche est l'email vérifié du compte, sinon demande au personnel) ; l'identifiant utilisé est enregistré sur la demande (`student_link_requests.identifier_type`) et affiché au relecteur.
- ADR-072 : l'email OTP du portail étudiant passe par la file d'attente (message chiffré `ShouldBeEncrypted`, après commit, 2 tentatives) au lieu d'un envoi synchrone, pour que l'écran de saisie s'affiche sans attendre le SMTP ; remplace la règle « aucun code sérialisé dans la file ». Worker de file obligatoire en production. Saisie du code en 6 cases, validation automatique au 6e chiffre, renvoi possible après 60 s.
- ADR-073 : suppression de la validation manuelle des rattachements (remplace ADR-037 et la revue d'ADR-071) : l'email prouvé par OTP/Google plus la date de naissance et un renseignement de la fiche (CIN, téléphone, email, ou nom + nom de la mère) suffisent à ouvrir la fiche. Contreparties : une fiche = un compte, réponse générique, limite de débit, email d'alerte à l'adresse officielle si elle diffère, détachement du compte par le personnel (`student_links.review`). Page `/student-links`, contrôleur et action de revue supprimés ; demandes en attente closes.

- ADR-074 : notifications persistantes du portail étudiant dans la cloche et `/notifications` : demandes de correction et confirmations, pour les comptes actifs et vérifiés de l'établissement déclarant dans l'année courante, la Scolarité Centrale et le superadmin selon leurs permissions. Developer et comptes student exclus des destinataires opérationnels, sans exclusion de l'audit. Écriture database synchrone dans la transaction métier (aucun email ni job de notification) : rollback commun et confirmation idempotente. Nom de l'étudiant et champ concerné seulement, jamais valeurs personnelles ni messages. Propriété, permissions et périmètre actuels recontrôlés pour la liste, le compteur et chaque action ; ouverture POST, destinations reconstruites côté serveur. Préférences personnelles par type, audit des préférences, pagination et filtres serveur, rafraîchissement toutes les 30 secondes ; les tâches à traiter restent indépendantes des états lu/non lu. Purge quotidienne des seules notifications étudiantes lues depuis plus de 90 jours.

- ADR-075 : boursiers et non-boursiers sans module d'inscription. La situation de l'année garde son origine (`source` : établissement, PNES, Scolarité, préinscription), sa vérification (`verified`, `pending`, `matched`) et le statut boursier ; l'identité reçoit code bourse, UIN et numéro de compte (chiffré, masqué ; UIN et compte réservés à la Scolarité Centrale et aux acteurs globaux, refusés venant d'un établissement). Trois imports typés (`student_imports.kind`) : liste d'établissement, base PNES (crée ou marque les boursiers, `verified` ; contacts inutilisables écartés au lieu de rejeter le boursier, doublon de CIN/code bourse/UIN toujours rejeté) et résultats de préinscription (admis seulement, L1/N par défaut). Saisie par la Scolarité (`students.register_pending`) = situation `pending`, `matched` quand la liste de l'établissement la contient, puis validée (`student_records.verify`) ; un dossier de bourse se reçoit mais ne se valide pas sur une situation non vérifiée. Quatre permissions nouvelles (`imports.pnes`, `imports.preinscription`, `students.register_pending`, `student_records.verify`), jamais attribuées aux établissements. Remplace les bornes d'ADR-033 : 20 000 lignes, lecture par passes de 2 000, analyse et confirmation en Jobs au-delà de 1 000 lignes (une tentative, 600 s, `retry_after` 660 s, worker obligatoire), retour à l'étape précédente en cas d'interruption.

- ADR-076 : validation automatique des situations saisies par la Scolarité, après confirmation réussie d’une liste d’établissement qui les retrouve. - ADR-077 : fiche d’étiquettes DDB vierges (`/scholarships/reception/labels`, permission dédiée `scholarships.labels`, superadmin seulement par défaut, attribuable aux autres rôles par la matrice des permissions). Feuille A4 de 10 étiquettes 2 × 5 de 99,1 × 57 mm (format des planches autocollantes courantes, bordures pointillées servant de traits de coupe sur papier ordinaire), imprimée par le navigateur. Chaque étiquette porte le nom de l’université, une ligne d’en-tête suivie de l’année de la campagne, la partie du modèle DDB placée avant et après `{NUM}`, résolue pour la campagne choisie (ouverte, ou programmée pour préparer les étiquettes à l’avance ; `{ETAB}`, inconnu à l’avance, reste un blanc `____`), une ligne soulignée pour écrire le numéro au stylo, un QR code standard vers le portail étudiant (défaut `SCHOLARSHIP_LABEL_URL`, `https://bourse.mahajanga-univ.mg`) et un pied de page, généré côté serveur en SVG (bacon/bacon-qr-code, déjà installé par Fortify). Le préfixe n’a pas de réglage propre : il suit le modèle DDB de Paramètres › Plateforme, pour que l’étiquette et le numéro généré à la réception ne divergent jamais. Les textes de l’étiquette sont réglables par le superadmin dans Paramètres › Plateforme › Étiquettes DDB (`branding.manage`, `platform_settings` : `ddb_label_heading` « Bourse nationale », `ddb_label_caption` « Numéro DDB », `ddb_label_hint` « Suivi du dossier en ligne », `ddb_label_footer` « Service Scolarité Centrale » imprimé en pied, `ddb_label_url` lien du QR code, adresse http(s) obligatoire) ; un champ vide reprend le texte par défaut ; aperçu en taille réelle ; audit `ddb_labels_updated` avec les champs et valeurs modifiés (textes publics, sans donnée personnelle). L’impression elle-même ne crée ni enregistrement ni audit (aucune donnée personnelle, rien n’est exporté). 1 à 20 feuilles par impression.

- ADR-080 : emails aux étudiants, envoyés à l’email officiel de la fiche quand il est renseigné, en file d’attente après commit et chiffrés dans la file (nom, N° DDB) : « Fiche étudiante enregistrée » à la création par le formulaire (jamais par un import, pour ne pas envoyer des milliers d’emails) et « Dossier de bourse reçu » à la réception du dossier papier (N° DDB, N° de dossier, campagne, date ; nouvel étudiant ou fiche existante). - ADR-081 : un seul numéro visible par dossier de bourse, le **N° DDB** (`ScholarshipApplication::reference()`) : tableau, fiche du dossier, réception, activité, corbeille, export Excel, emails et messages. Le numéro technique `BRS{campagne}-{séquence}` reste en base comme clé interne unique sur toute la plateforme (le N° DDB n'est unique que dans sa campagne : deux campagnes de la même année avec `DDB-{ANNEE}-{NUM}` produiraient le même numéro) ; il n'est plus affiché, la recherche l'accepte encore, et il ne remplace le N° DDB que pour un ancien dossier sans DDB. - ADR-082 : **une seule demande de bourse par étudiant et par année universitaire**, toutes campagnes confondues (avant : une par campagne). Contrôle dans `ReceiveScholarshipApplication` (scope `ScholarshipApplication::ofStudentYear`, sous le verrou de la fiche étudiante qui sérialise deux guichets) et à la restauration depuis la corbeille (`TrashManager`). La réception affiche le dossier de l'année comme « déjà reçu », même déposé dans une autre campagne. L'index SQL `(campagne, étudiant)` reste en filet de sécurité.

- ADR-083 : statut affiché « En attente de la liste » (`awaiting_list`) pour un dossier reçu (`pending`) dont la situation n'est pas encore confirmée par la liste de l'établissement (`verification` ≠ `verified`, par exemple une saisie de la Scolarité Centrale). **Calculé, jamais enregistré** (`ScholarshipApplication::displayStatus()`) : il redevient « Reçu » de lui-même dès l'import de la liste, sans tâche de synchronisation. - ADR-084 : **validation rapide depuis la liste** des dossiers (bouton « Décider » d'une ligne ou sélection). Les contrôles encore « à faire » sont enregistrés conformes au nom de l'agent par `UpdateScholarshipCheck` (audit `check_updated` par contrôle, passage par « En vérification » dans l'historique), puis le dossier est validé, le tout dans une transaction. Bloquent toujours : un contrôle non conforme, une situation non confirmée par la liste de l'établissement, une fiche ou situation désactivée (rien n'est alors modifié). La fiche du dossier garde la validation stricte, contrôle par contrôle. `ValidationBlockers::for($dossier, true)` donne les raisons affichées dans la liste.

- ADR-085 : suppression du module Campagnes : la bourse nationale est unique et chaque dossier appartient directement à une **année universitaire**. La réception utilise uniquement l’année courante active ; aucune année courante ferme la réception. Une demande active par étudiant et par année, garantie en SQL par un marqueur calculé hors corbeille ; la restauration vérifie aussi cette règle. Les DDB restent uniques par année, corbeille comprise. Les séquences et leurs compteurs passent aux années sans réutiliser les numéros déjà attribués ; en présence de plusieurs anciennes campagnes, leurs plages sont décalées. Les DDB et numéros techniques existants restent inchangés. Les nouveaux numéros techniques sont `BRS-{année universitaire}-{séquence}`. Les étiquettes choisissent une année active, courante en premier. Routes, navigation et permissions `campaigns.*` supprimées ; les anciens événements d’audit restent lisibles. La migration refuse les conflits avant toute modification ; sauvegarde et arrêt des écritures requis lors de son application. Le rollback recrée une campagne nationale par année, sans retrouver les anciens libellés ni permissions ; il refuse les doublons étudiant/année, corbeille comprise, avant tout changement. Cette décision remplace les règles de campagne des ADR-042, 077 à 082.
